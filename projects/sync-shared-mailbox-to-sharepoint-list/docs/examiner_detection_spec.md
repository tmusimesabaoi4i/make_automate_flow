## 1. 用語定義

| 用語 | 定義 |
|---|---|
| **現在のメッセージ** | 正規化済み本文を「スレッド区切り語」で分割した**先頭の区画**（§4） |
| **引用メッセージ** | 2番目以降の区画。深度1（直前の引用）と深度2以上（さらに古い引用）を区別する |
| **区画（section）** | 上記の分割単位。深度 0 / 1 / 2 の3値で表す |
| **候補（candidate）** | アンカー語の k 番目の出現から切り出した1件の推定結果。スコア・区画・根拠を持つ |
| **アンカー** | 候補の切り出し起点になる語（`担当審査官:` `審査官` `様` `特許庁の` など） |
| **スロット** | アンカーの k 番目の出現。パターンごとに見る個数を決める（§6.2） |
| **姓のみ** | 空白を含まず3文字以下の氏名。`FamilyNameOnly` |
| **フルネーム** | 空白を含む、または4文字以上の氏名。`FullName` |
| **ひらがな表記** | 全体がひらがなの氏名。`HiraganaName`。**漢字へは変換しない** |
| **補完** | 姓のみの候補を、同一スレッド内の証拠でフルネームへ置き換えること（§10） |
| **要確認** | `needsManualReview = true`。人が確認すべき状態。値は返すが確定扱いにしない |

## 2. 前提条件

### 2.1 入力

| 入力 | 出どころ |
|---|---|
| 本文 | `variables('varItemBodyText')`（Content Conversion `HtmlToText` の出力）。**HTMLのままでは判定しない** |
| 件名 | `outputs('Compose_Subject')` |
| 送信元 | `outputs('Compose_Sender')`（§11 のメールアドレス判定にのみ使用） |

### 2.2 Power Automate 側の制約（実装形を決めている理由）

| 制約 | 実装への影響 |
|---|---|
| **正規表現が無い** | `FindAllMatches` は実装不可。`split` によるアンカー分割で先頭N件を取る（§6.2） |
| ループを増やせない | 最大ネスト深さが 7/8。検出は `Foreach_Email` 直下の**平坦な Compose 連鎖**にする |
| **アクション上限 500** | 現在 491。パターンごとのスロット数はここから逆算して決めている |
| 1式 8,192 文字 | 文脈・近傍を1つのオブジェクトにまとめて参照を短くしている（現在の最長式 6,693） |
| `substring` は範囲外でエラー | 必ずパディングしてから**定数オフセット**で切る |
| `sort` は昇順のみ | 降順は `reverse` 併用。キーは**桁数を揃えた文字列**（§8） |
| `if()` は両分岐を先に評価 | 使わない側の分岐にも安全な値（センチネル）を渡す |

### 2.3 検出は同期を止めない

検出処理は**コネクタを1つも呼ばない**（すべて `Compose` / `Query`）。
検証スクリプト P4 が機械確認する。推定に失敗しても他の5列は登録される。

### 2.4 本機能が使わないもの

- **審査官名簿（ExaminerDirectory）はリポジトリ内に存在しない。** 名簿由来の補完は実装しない
- **Teamsメンバー一覧・SharePointユーザー一覧を人物の照合に使わない。**
  同姓者がいることを理由に人物を確定しない（資料§6）
- メールヘッダの `To` / `Cc` は参照しない。本文テキスト中の `Cc:` という**文字列**だけを見る

## 3. 正規化仕様

本文・件名の両方に適用する。**人名そのものは変えない**（数字・記号・空白と定型誤記だけ）。

| 順 | 処理 | 内容 |
|---|---|---|
| 1 | HTMLエンティティ復元 | `&gt; &lt; &quot; &#39; &nbsp; &amp;`。**`&amp;` を最後**に置換（二重復元の防止） |
| 2 | 制御文字 | CR 除去、タブ→半角空白 |
| 3 | 全角数字 | `０`〜`９` → `0`〜`9` |
| 4 | ハイフン類 | `－ ー − – — ‐` → `-` |
| 5 | 約物 | 全角空白→半角空白、`：`→`:`、`，`→`,`、`（）`→`()` |
| 6 | 連続空白 | 4→1 / 3→1 / 2→1 の順に圧縮 |
| 7 | 定型誤記 | `審審査第四部`→`審査第四部`、`特許庁審査官`→`特許庁 審査官` |

> 7 は本文のみに適用する（件名には掛けない）。

## 4. メールスレッド分割仕様

### 4.1 区切り語

```
-----Original Message-----   差出人:   送信日時:   From:   Sent:   wrote:   On
```

各出現の**直前**にセンチネル `<<<TS>>>` を差し込み、センチネルで `split` する。

- `Compose_Det_Current` = 先頭の区画（**現在のメッセージ**）
- `Compose_Det_Through1` = 先頭2区画の連結（**現在＋直前の引用**）

### 4.2 深度の決め方

区画そのものを配列として持ち回ることはできない（ループが無い）ので、
**「アンカーの k 番目の出現が、どの範囲までに収まっているか」**で決める。

```
curOcc = 現在の区画に含まれるアンカーの出現数
th1Occ = 現在＋直前の引用に含まれるアンカーの出現数

深度(k) = 0 (現在)          if k <= curOcc
        = 1 (直前の引用)     else if k <= th1Occ
        = 2 (さらに古い引用)  otherwise
```

**深度2以上はすべて同じ扱い**になる（段数を数える手段が無い。§13-4）。

## 5. 出願番号の抽出仕様

### 5.1 抽出

`split(正規化本文, '特願')` の k 番目（k = 1..5）の直後、および件名から1件。

```
Padded  = concat(空白とカンマを除いた先頭24文字, '                ')   ← 16文字パディング
Core12  = substring(Padded, 0, 12)   Core11 = substring(Padded, 0, 11)   Core10 = substring(Padded, 0, 10)

6桁として妥当 = Core11 から数字を除くと '-' だけ残る
              AND Core12 から数字を除いても '-' だけ残る ことはない   ← 7桁以上を弾く
5桁として妥当 = Core10 から数字を除くと '-' だけ残る
              AND Core11 から数字を除いても '-' だけ残る ことはない

番号 = 6桁妥当なら Core11 / 5桁妥当なら Core10 / どちらでもなければ空
```

**7桁の連番から先頭6桁を黙って採らない。** 形式不正なら空にする。

### 5.2 保存形式

`YYYY-NNNNNN`（`特願` は付けない）。5桁の場合は `YYYY-NNNNN`。

### 5.3 スコアリング表

| 項目 | 点 | 条件 |
|---|---|---|
| 基礎点 | **50** | すべての候補 |
| 件名 | **+180** | 件名から採った候補（決定規則12「件名を強く優先」） |
| 区画 | **+100 / −20 / −60** | 現在 / 直前の引用 / さらに古い引用 |
| ラベル | **+40** | 前後64文字に `出願番号` |
| 話題語 | **+20** | 前後64文字に `案件` `標記` `表題` `本件` |
| 別件・誤送信 | **−80** | 前後64文字に `別件` `誤り` `誤送信` |
| 一貫性 | **+10〜+40** | 同じ番号が本文に2/3/4/5回以上出る |

定義箇所は `build_examiner_flow.py` の `APP_SCORES`。**式の中に即値を書かない。**

## 6. 審査官候補の抽出仕様

### 6.1 パターン

| ID | パターン | アンカー | 方向 | 基礎点 | 資料の PATTERN |
|---|---|---|---|---|---|
| T | 担当審査官ラベル | `担当審査官:` | 前方 | **100** | — |
| R | 役職の直後 | `審査官` / `審査官補` | 前方 | 80 | 5 |
| N | 役職の直前 | `審査官` の前 | 後方 | 75 | 3・4・6・7・8・9・12 |
| L | その他ラベル | `審査官:` / `ご担当者:` | 前方 | 60 | — |
| I | 自己紹介 | `特許庁の` / `伝送システムの` | 前方 | 55 | 10 |
| D | 部署宛名 | `様` の前 | 後方 | 45 | 1・2 |
| S | 件名のラベル | `担当審査官:` / `審査官:` | 前方 | 60+60 | — |

資料の PATTERN 11「特許庁[部署] [フルネーム]」（敬称も役職も無い署名）は
**スコア対象にせず**、§10 の補完と姓の切れ目判断にのみ使う（§6.4）。

### 6.2 スロット数（アクション上限からの逆算）

```
T:3  R:3  N:3  L:2  I:2  D:2   ＝ 15候補（1候補につき Compose 3つ）
```

強い手掛かり（T/R/N）に枠を厚く配分している。

### 6.3 切り出しと整形

1. 前方は直後24文字、後方は直前24文字を取る
2. 区切りで切る:
   - 共通: `様 さま 殿 先生 御中 、 。 ・ , . ( ) : ; [ ] 【 】 < > " / | @ です でございます と申します 宛 各位 -`
   - **装飾記号**: `＊ * ＝ = ─ ━ ＿ _ ● ○ ■ □ ▲ △ ※ ～ ~ ＋ ＃ ＄ ％ ＆ ！ ？ …`
   - 後方のみ追加: 助詞 `は が を に へ と も で や の から より ます でした います 本日 昨日 先日 今回`
   - 改行・タブ
   - **半角スペースは区切りにしない**（姓名間の空白を保つため）
3. 敬称・役職・既知の組織名を除去（`審査官補` → `審査官` の順）
4. **末尾トークンで氏名を決める**（下記）

#### 末尾トークンによる氏名の切り出し

除去リストは**リストに載っていない部署の実名**を消せない。そこで構造で決める。
人名は空白区切りの**末尾1〜2トークン**で、それより前は組織名。

| 末尾トークン | 直前トークン | 結果 |
|---|---|---|
| 4文字以上 | — | 末尾トークンがそのまま氏名 |
| 1〜3文字 | 2〜3文字・平仮名始まりでない | 姓とみなして結合 |
| 1〜3文字 | それ以外 | 末尾トークンのみ |

直前トークンに**2〜3文字**を要求するのが要点。日本語の姓はこの長さに収まるが、
部署名（`医療機器` `審査第◯部◯◯`）はまず収まらない。

### 6.4 妥当性

すべて満たすときだけ候補にする。

- 長さ 2〜12
- 数字を含まない
- 除外語を含まない:
  `弁理士 代理人 出願人 発明者 担当者 御中 各位 事務所 法人 部長 課長 係 会社 部 陪席 同席`
- **先頭2文字が平仮名でない**（下の例外を除く）

#### ひらがな氏名の例外（資料 PATTERN 12）

「先頭2文字が平仮名なら人名としない」は、実メールで `〜に加えて◯◯ 審査官` から
`加えて◯◯` を人名にした誤検出への対策で、**維持する**。
ひらがな姓は次を**すべて**満たすときだけ例外的に受け入れる。

- **全体がひらがな**（`加えて米倉` `にご対応` は漢字混じりなので従来どおり却下）
- 長さ 2〜6
- 機能語（`ました います ください よろしく ありがとう お世話 いただき ございます` ほか）を含まない
- パターンが **T / R / N / L / I / S**（役職語・ラベル・自己紹介が隣接）。
  **D（部署宛名・基礎点45）は対象外**——手掛かりが弱すぎる

受け入れた場合は `NameType = HiraganaName`、スコア **−30**、**要確認**にする。
**漢字へは変換しない**（読みの照合表が無い。§13-2）。

### 6.5 スコアリング表

| 項目 | 点 | 条件 |
|---|---|---|
| 基礎点 | 45〜160 | §6.1 のパターン別 |
| 区画 | **+100 / −20 / −60** | 現在 / 直前の引用 / さらに古い引用 |
| 冒頭の宛名付近 | **+40** | 現在の区画の**先頭200文字**に氏名が出る |
| 特許庁・部署に近接 | **+40** | 直前24文字に `特許庁` `審査第一〜四部` `伝送システム` `移動体通信システム` |
| 担当審査官 | +40 | 前後64文字に `担当審査官` |
| ご担当 | +20 | 前後64文字に `ご担当` |
| 敬称 | +10 | 前後64文字に `様` `殿` `先生` |
| 出願番号と同区画 | **+30** | 採用した出願番号と**同じ深度**にいる |
| 反復出現 | **+20** | 同じ氏名が本文に2回以上出る |
| ひらがな表記 | **−30** | 全体がひらがな（漢字表記より弱い証拠） |
| 外部関係者 | **−100** | **直前24文字**に `弁理士 代理人 出願人 発明者 株式会社 特許事務所 法律事務所 弁理士法人` |
| Cc | **−80** | **直前12文字**に `Cc:` `CC:` `cc:` |
| 参加者 | **−60** | **直前12文字**に `参加者` `出席者` `同席` |

定義箇所は `EX_SCORES`。**式の中に即値を書かない。**

> **文脈窓を前方に限る理由**: 修飾語・肩書き・除外の手掛かりは対象の**前**に来る。
> 前後64文字で見ていたときは「審査官への挨拶 → 直後に差出人（弁理士）の署名」という
> ごく普通のメールで、宛名の審査官が −100 されて落ちていた。

## 7. 誤検出防止

### 7.1 減点では足りないもの（候補ごと除外）

氏名の**直前12文字**に次があれば、その候補は `Filter array` で除外する。

```
陪席  同席  参加者  出席者  Cc:  CC:  cc:  弁理士  代理人  出願人  発明者  事務所  法人  株式会社
```

減点だけだと「候補がそれしか無い」場合に採用されてしまうため。

### 7.2 「Ccだけを理由に除外しない」（資料§3.5）への適合

**除外は出現位置ごとであって氏名単位ではない。**
同じ人物が本文の別の箇所で `審査官` として現れれば、そちらの候補は生き残り採用される。
したがって「Ccに含まれることだけを理由に除外」はしていない。

| ケース | 挙動 |
|---|---|
| Cc欄に審査官と**同姓の別人**がいて、本文に明示の審査官がいる | 本文側が採用される（テスト V04） |
| **Cc欄にしか**審査官の記載が無い | 採用しない（証拠が1つだけ。テスト X02） |

### 7.3 判定窓を狭く保つ理由

陪席・Cc・参加者の判定に**直前12文字だけ**を使うのは、後方64文字まで見ると
「主担当審査官の後に陪席審査官が書かれているだけ」で主担当まで除外されてしまうため。

## 8. 最良候補の選択と同点処理

```
有効候補 = すべての候補から §6.4 の妥当性と §7.1 の除外を通ったもの
順位     = first(reverse(sort(有効候補, 'k')))
```

`sort` は昇順の**文字列**比較しかできないため、キーは次の連結にする。

```
k = string(スコア + SORT_OFFSET) + パターン優先度(1桁) + (2 − 深度)(1桁)
```

- `SORT_OFFSET = 20000`。**「スコア＋オフセット」が常に5桁**であることが正しさの条件。
  桁数が揃わないと `"9990" > "10150"` となり、**スコアが低いほうが勝つ**。
  生成時に `assert` で範囲を確認している（下記）
- パターン優先度: `T,S = 6 > R = 5 > N = 4 > L = 3 > I = 2 > D = 1`
- 深度: 現在(2) > 直前の引用(1) > さらに古い引用(0)

> **同点規則は資料に無いため新設した。** 規定しないと実機の `sort` の安定性に依存し、
> 同点時の結果が不定になる。

```python
# build_examiner_flow.py — 生成時に桁あふれ／桁落ちを検出する
_assert_sort_key_width(EX_SCORES, [45, 160], "EX_SCORES")
```

## 9. 確信度の判定

| 対象 | 判定 |
|---|---|
| 審査官 | 空 → `Not Found` ／ スコア<60 → `Low` ／ 次点との差<15 → `Ambiguous` ／ スコア≥180 → `High` ／ 他 → `Medium` |
| 出願番号 | 空 → `Not Found` ／ 次点との差<15 → `Ambiguous` ／ スコア≥160 → `High` ／ ≥100 → `Medium` ／ 他 → `Low` |

**要確認 (`needsManualReview`)** は次のいずれか:

- どちらかが `Not Found` / `Low` / `Ambiguous`
- 審査官の `NameType` が `FamilyNameOnly` または `HiraganaName`（＝確定していない）

## 10. 氏名補完仕様

### 10.1 補完の順序（資料§4）

1. 同一スレッド内（現在・引用）の候補に、その姓で始まるより長い氏名があるか
2. 特許庁側の**署名・自己紹介**にフルネームがあるか
   （組織名アンカーの**先頭2件と末尾2件**の直後から採る。署名は本文末尾にあるため）
3. 同じ出願番号に関する区画に対応するフルネームがあるか → **区画一致は §6.5 の加点で表現**
4. 審査官名簿 → **存在しないので使わない**

### 10.2 補完してよい条件

**異なる氏名がちょうど1種類**のときだけ。
候補の**行数**ではなく**異なる名前の種類数**で数える（同じ名前を複数のパターンが拾うのは普通に起きる）。

### 10.3 補完してはならない条件

- 同じ姓の候補が複数存在する
- ひらがな表記（読みの照合表が無いため対応関係を確認できない）
- 証拠がスレッド内に無い

補完できない場合は**姓またはひらがな表記のまま保持**し、`NameType` を
`FamilyNameOnly` / `HiraganaName` にして**要確認**にする。**未検証のフルネームを生成しない。**

### 10.4 姓名の間の半角スペース

列には `姓 名` の形（半角スペース1個）で保存する。切れ目の根拠は次の順で採る。

| | 規則 | 例 |
|---|---|---|
| A | 既に空白がある → そのまま | `中村　ノア` → `中村 ノア` |
| B | 空白除去形が一致する空白付き候補がちょうど1種類 | 引用部の `吉村 真治郎` |
| C | 接頭辞になっている姓がちょうど1種類 | 署名 `特許庁 中野` → `中野志保子` を `中野 志保子` |
| D | 根拠が無く**4文字ちょうど**（かつ**ひらがなでない**） | `伊東和重` → `伊東 和重` |
| E | 根拠が無く5文字以上、またはひらがな表記 | 切らない |

規則Cの姓の出どころ: ①組織名アンカーの直後 ②有効候補 ③**既知の3文字姓の表**（20語）。
3文字姓の表を持つのは、規則Dの 2＋2 という既定を上書きする必要があるのが3文字姓だけだから。
**2文字の姓は表に入れない**（`長谷部` を `長谷／部` と切ってしまう）。

> 規則Dを**ひらがなに適用しない**のは、`おうさか` を `おう さか` と切る根拠が無いため。

## 13. 資料から変更・不採用にした点

| # | 資料 | 判断 | 理由 |
|---|---|---|---|
| 1 | `FindAllMatches`（全位置探索） | 不採用 | WDLに正規表現・位置走査が無い。`split` アンカーで先頭N件（§6.2） |
| 2 | `ReadingOf()`（読み一致での補完） | **不採用** | 漢字→読みの変換表が無い。ひらがな候補は変換せず保持し要確認にする |
| 3 | `OptionalExaminerDirectory`（名簿） | **不採用** | リポジトリ内に存在しない。名簿由来の補完(+10)も実装しない |
| 4 | `Score − (threadDepth × 20)` | 3段階の定数へ | 段数を数える手段が無い。深度2以上は同一扱い |
| 5 | 「役職隣接 +80」の独立加点 | **基礎点に統合** | R(80)/N(75) の基礎点が既に役職隣接を表しており、**二重計上**になる |
| 6 | 署名／転送ヘッダー／参加者一覧／宛先Cc の**区画分割** | 近傍語で近似 | 行単位の走査ができない。直前12〜24文字の語で判定する |
| 7 | `GetSurroundingText(text, pos, 80)` | 前後64文字＋直前12/24文字 | 位置が取れないため、アンカー分割の前後要素から取る。窓を用途別に分けたのは §6.5 の注記のとおり |
| 8 | `CleanCandidateName` の中身が未定義 | §6.3 で具体化 | 区切り・除去語・末尾トークン規則を明文化した |
| 9 | `SplitEmailThread` の分割規則が未定義 | §4 で具体化 | 区切り語7種とセンチネル方式を明文化した |
| 10 | `current message` の判定が未定義 | §4.2 で具体化 | 「アンカーの k 番目の出現が現在区画の出現数以内か」で判定する |
| 11 | 同点時の決定規則が無い | **新設** | §8。規定しないと実機の `sort` の安定性に依存して結果が不定になる |
| 12 | 確信度の定義が無い | **新設** | §9 |
| 13 | 「主担当審査官」と「宛先の審査官」の区別が無い | 区別しない | 本文からは判別できない。陪席・参加者は除外しているので実質は主担当に寄る |
| 14 | 複数案件メールへの対応が不十分 | 次点との差<15 を `Ambiguous` にする | 1通で2案件が同程度に言及される場合を**要確認**にする（テスト Y04） |

## 14. 既知の制限事項

| 制限 | 内容 |
|---|---|
| アクション数 | **491 / 500**。残り9。パターン・スロットを増やす余地はほぼ無い |
| 探索範囲 | 本文は `特願` 5件・審査官はパターンごと2〜3件まで。それ以降の出現は見ない |
| スレッド深度 | 深度2以上を区別しない（3階層目と10階層目が同じ扱い） |
| ひらがな氏名 | 漢字へ変換しない。常に要確認 |
| 姓名の空白（4文字） | 根拠が無い4文字は 2＋2 で切る。`林健太郎` のような**1文字姓＋3文字名**は誤る |
| 3文字姓の表 | 20語のみ。表に無い3文字姓の4文字氏名は 2＋2 で誤分割する。誤りを見つけたら `KNOWN_SURNAMES_3` に追記する |
| `の` の除去 | 候補名の整形で `の` を除去する（`特許庁の山田`→`山田`）。`井の頭` のような姓は壊れる |
| 部署宛名パターン | 行単位の走査ができないため「`様` の直前＋文脈の部署語」で近似している |
| メールアドレス | 自己紹介がある場合しか出せない。名簿・メンバー一覧からは引かない |
