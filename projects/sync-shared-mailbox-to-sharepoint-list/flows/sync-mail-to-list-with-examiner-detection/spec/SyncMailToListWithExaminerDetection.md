## 1. 目的

既存フロー `sync-mail-to-list` と同じ同期処理に加えて、
**メールの件名とプレーンテキスト本文から「審査官名」と「出願番号」を推定**し、
SharePointリストの専用列へ登録する。

推定に失敗しても他の5項目は登録し、**メール同期そのものは止めない**。

## 5. 審査官名の推定方法

### 5.1 入力と正規化

入力は `variables('varItemBodyText')`（Content Conversion で変換済みのプレーンテキスト）と
`outputs('Compose_Subject')`。HTMLのままでは判定しない。

正規化: HTMLエンティティ復元 → 全角空白/タブ→半角・CR除去 → 全角数字→半角 →
ハイフン類統一 → 全角コロン等→半角 → 連続空白の圧縮 → 定型誤記の補正
（`審審査第四部`→`審査第四部`、`特許庁審査官`→`特許庁 審査官`）。
**人名そのものは変えない**（数字・記号・空白と定型誤記だけを直す）。

### 5.2 スレッドの扱い

`-----Original Message-----` / `差出人:` / `送信日時:` / `From:` / `Sent:` / `wrote:` / `On `
の直前にセンチネルを差し込み、**最初のセクション＝現在のメール本文**とする。

先頭2区画の連結（`Compose_Det_Through1`）も作り、深度を**3段階**に分ける。

候補がどの区画に属するかは「そのアンカーの k 番目の出現が、どの範囲までの出現数に
収まっているか」で判定する。

| 深度 | 意味 | 審査官 | 出願番号 |
|---|---|---|---|
| 0 | 現在のメッセージ | **+100** | **+100** |
| 1 | 直前の引用 | −20 | −20 |
| 2 | さらに古い引用 | **−60** | **−60** |

> 深度2以上はすべて同じ扱いになる（段数を数える手段が無い）。§13 の既知の制約。

### 5.3 抽出パターン（6種・パターン別スロット＋件名1件＝最大16候補）

| ID | パターン | アンカー | 基礎点 | スロット |
|---|---|---|---|---|
| T | 担当審査官ラベル | `担当審査官:` | **100** | 3 |
| R | 役職の直後 | `審査官` / `審査官補` | 80 | 3 |
| N | 役職の直前 | `審査官` の前 | 75 | 3 |
| L | その他ラベル | `審査官:` / `ご担当者:` | 60 | 2 |
| I | 自己紹介 | `特許庁の` / `伝送システムの` → `です`まで | 55 | 2 |
| D | 部署宛名 | `様` の前 | 45 | 2 |
| S | 件名のラベル | `担当審査官:` / `審査官:` | 60＋60 | 1 |

正規表現が無いため、**アンカーで `split` して k 番目の出現を取り出す**方式で代替している。
スロット数は500アクション上限からの逆算で、強い手掛かり（T/R/N）に厚く配分している。

### 5.4 候補の整形と妥当性

敬称・役職・組織名を除去（`審査官補`→`審査官` の順で処理）してから trim する。
区切りは `様 さま 殿 先生 御中 、 。 ・ , . ( ) : ; [ ] 【 】 < > " / | @ です でございます と申します 宛 各位 -`、
**装飾記号**（`＊ * ＝ = ─ ━ ＿ _ ● ○ ■ □ ▲ △ ※ ～ ~ ＋ ＃ ＄ ％ ＆ ！ ？ …`）、改行・タブ。
**半角スペースは区切りにしない**（`山田 太郎` の姓名間の空白を保つため。指示§9.1）。

> 装飾記号を区切りに入れているのは、HTMLメールをテキスト化したものでは
> 注意書きの罫線と宛名が1行に潰れて入ってくるため
> （`＊＊＊…＊＊ 審査第◯部◯◯ 山田太郎 審査官殿`）。これらは日本語の人名に現れない。

#### 末尾トークンによる氏名の切り出し

区切りで切っても、**部署の実名は前に残る**。`CLEAN_STRIP` は既知の組織名しか消せない。

```
「＊＊＊＊＊＊ 審査第◯部◯◯◯ 山田太郎」   → 山田太郎
「◯◯◯◯ 審査第◯部◯◯◯ 山中 実」         → 山中 実
```

そこで**構造**で決める。人名は空白区切りの**末尾1〜2トークン**で、それより前は組織名。

| 末尾トークン | 直前トークン | 結果 |
|---|---|---|
| 4文字以上 | — | 末尾トークンがそのまま氏名（直前は組織名） |
| 1〜3文字 | 2〜3文字・平仮名始まりでない | 姓とみなして結合（`山中` + `実`） |
| 1〜3文字 | 上記以外（4文字以上／平仮名始まり） | 末尾トークンのみ |

直前トークンに**2〜3文字**を要求するのが要点。日本語の姓はこの長さに収まるが、
部署名（`医療機器` `審査第◯部◯◯`）はまず収まらない。

後方切り出し（パターン N・D）では、加えて助詞
`は が を に へ と も で や の から より ます でした います 本日 昨日 先日 今回` でも切る。
（`本日は山田太郎 審査官` → `山田太郎`）

妥当性: 長さ2〜12 ／ 数字を含まない ／ **先頭2文字が平仮名でない** ／
除外語（`弁理士 代理人 出願人 発明者 担当者 御中 各位 事務所 法人 部長 課長 係 会社 部 陪席 同席`）を含まない。

> **先頭2文字**を見るのは、後方切り出しが助詞で切っても
> 「〜に加えて○○」「〜として○○」のように動詞・接続語が残るため。
> 1文字だけでは弾けない（実メールで `加えて米倉…` を人名にした）。
> 日本語の姓は先頭2文字が平仮名にならないという**字種の規則**を使っている。
> 2文字目までしか見ないので `井上さゆり` のように名が平仮名の人名は残る。

#### ひらがな氏名の例外

`さとう 審査官殿` のような**ひらがな姓**は、次を**すべて**満たすときだけ受け入れる。

- **全体がひらがな**（`加えて米倉` `にご対応` は漢字混じりなので従来どおり却下）
- 長さ 2〜6 ／ 機能語（`ました います よろしく お世話` ほか）を含まない
- パターンが **T / R / N / L / I / S**（役職語・ラベル・自己紹介が隣接）。**D は対象外**

`examinerNameType = HiraganaName` として記録し、**漢字へは変換しない**（読みの照合表が無い）。
スコア −30 かつ**常に要確認**。姓名の空白挿入（§5.7 規則D）も適用しない。

### 5.5 加減点

すべて `build_examiner_flow.py` の `EX_SCORES` / `APP_SCORES` に集約している
（式の中に即値を書かない。補助資料§3.4「定数として管理し根拠を追跡できる構造にする」）。

| 加点 | 減点 |
|---|---|
| 文脈に `担当審査官` +40 | **直前24文字**に `弁理士/代理人/出願人/発明者/株式会社/特許事務所/法律事務所/弁理士法人` **−100** |
| 文脈に `ご担当` +20 | 直前12文字に `Cc:/CC:/cc:` −80 |
| 文脈に `様/殿/先生` +10 | 直前12文字に `参加者/出席者/同席` −60 |
| **現在の区画 +100** | **直前の引用 −20 ／ さらに古い引用 −60** |
| **冒頭200文字に氏名 +40** | **全体がひらがな −30** |
| **直前24文字に `特許庁`/部署名 +40** | |
| **採用した出願番号と同じ区画 +30** | |
| **同じ氏名が本文に2回以上 +20** | |

適用された項目は候補ごとに記録され、診断の `examinerEvidence` に
`p=T;base=100;section=0;tantou;head;jpo-near` の形で出る。

さらに**除外**（減点では足りないため。下記参照）:

名前の**直前12文字**に `陪席 同席 参加者 出席者 Cc: CC: cc: 弁理士 代理人 出願人 発明者 事務所 法人 株式会社`
があれば、その候補は **Filter array で除外**する（減点だけだと「候補がそれしか無い」場合に採用されてしまうため）。

> 陪席・Cc の判定に**直前12文字だけ**を使うのは、後方64文字まで見ると
> 「主担当審査官の後に陪席審査官が書かれているだけ」で主担当まで除外されてしまうため
> （テスト E07 で検出した不具合）。
>
> 外部関係者（弁理士など）の減点も同じ理由で**直前24文字**に限る。
> 前後64文字で見ていたときは、「審査官への挨拶 → 差出人（弁理士）の署名」という
> ごく普通のメールで、宛名の審査官が −100 されて落ちていた（実メールで検出。R01・R04）。
> **修飾語は名前の前に来る**——これが範囲を前方に限る根拠。

### 5.6 最良候補の選択と姓のみ補完

スコアを文字列のソートキーにして `first(reverse(sort(候補, 'k')))` で選ぶ
（`sort` は昇順のみのため `reverse` を併用）。ループを使わない。

```
k = string(スコア + 20000) + パターン優先度(1桁) + (2 − 深度)(1桁)
```

- **「スコア＋オフセット」が常に5桁であること**が正しさの条件。桁数が揃わないと
  `"9990" > "10150"` となり**スコアが低いほうが勝つ**。生成時に `assert` で検査している
- 同点時は パターン優先度（`T,S > R > N > L > I > D`）→ 浅い区画 の順で決める。
  **補助資料に同点規則が無いため新設**した（実機の `sort` の安定性に依存させない）

姓のみ（3文字以下）の場合、`Filter_Ex_Completion` で
「その姓で始まり、かつより長い候補」を抽出し、**異なる名前がちょうど1種類のときだけ**
フルネームへ補完する（名前で並べ替えて先頭と末尾が一致するかで判定する。
同じ名前を複数のパターンが拾うのは普通に起きるため、候補の**行数**では数えない）。
0件または2件以上なら補完せず、`needsManualReview` を立てる（指示§9.3）。

補完の候補には、スコア対象の候補に加えて**組織名アンカー由来の名前**も含める。
`特許庁審査第◯部◯◯◯　青木　健` のような**敬称も役職も付かない署名**は
どのパターンのアンカーにも掛からないが、ここには姓名が揃って書かれているため。
組織名アンカー（`特許庁 審査第一〜四部 伝送システム 移動体通信システム`）の
**先頭2件と末尾2件**の直後を見る（宛名は先頭に、署名は末尾に置かれる。
長い引用スレッドでは組織名が8回以上出るので、先頭だけを見ると署名を取りこぼす）。
これらは妥当性検査を通っていないので、補完時に長さと数字を確認する。

### 5.7 姓名の間の半角スペース（利用者決定 2026-08-04）

列には `姓 名` の形（半角スペース1個）で保存する。ただし——

> **根拠があるならそれを使う。無いときだけ既定に落とす。**
> 文字数だけで決め打つと、佐々木・長谷川のような3文字姓を必ず誤分割する。
> そこで、切れ目の根拠をまず**同じスレッドの中の実データ**から探す。

適用順（先に成立したものを使う）:

| | 規則 | 例 |
|---|---|---|
| A | 既に空白がある → そのまま（正規化で全角空白は半角1個になっている） | `中村　ノア` → `中村 ノア` |
| B | 空白除去形が一致する**空白付きの候補**がちょうど1種類ある → それを採用 | 引用部に `吉村 真治郎` |
| C | その氏名の**接頭辞になっている姓**がちょうど1種類ある → そこで切る | 署名 `特許庁 中野` から姓 `中野` → `中野志保子` を `中野 志保子` |
| D | 根拠が無く、**4文字ちょうど** → 2＋2 で切る | `伊東和重` → `伊東 和重` |
| E | 根拠が無く、5文字以上 → **切らない** | `桐生慎太郎` のまま |

規則Cの姓は3つの出どころから採る。**いずれもスコアには参加させない**——切れ目を決めるためだけに使う。

1. 組織名アンカー（`特許庁 審査第一部〜第四部 伝送システム 移動体通信システム`）の直後
   （署名 `特許庁 中野` ／ 自己紹介 `特許庁の相馬です`）
2. 既存の有効候補（`○○様` などで採れた姓のみ候補）
3. **既知の3文字姓の表**（`佐々木 長谷川 五十嵐 小笠原 …`）

3 を持つのは、規則Dの 2＋2 という既定を上書きする必要があるのが3文字姓だけだから。
**2文字の姓は表に入れない**——`長谷部` を `長谷／部` と切ってしまうため。

姓として採る条件: 長さ2〜4 ／ 数字・空白を含まない ／ 先頭2文字が平仮名でない ／
対象の氏名の**真の接頭辞**であること。**異なる姓が2種類以上あるときは規則Dへ落ちる**。

採用根拠は `Compose_Detection_Diagnostics.examinerSpacingSource`
（`original` / `variant` / `surname` / `none`）に残るので、実行履歴で確認できる。

## 6. 出願番号の推定方法

### 6.1 抽出（最大6候補：本文5＋件名1）

`split(正規化本文, '特願')` の k 番目の出現直後を取り出し、空白とカンマを除去してから
**16文字のパディングを連結**し、定数オフセットで切る。

```
Padded  = concat(空白カンマ除去済みの先頭24文字, '                ')
Core11  = substring(Padded, 0, 11)     Core10 = substring(Padded, 0, 10)
数字を全除去した結果が '-' なら妥当 → 6桁優先、なければ5桁
6桁と判定するには**12文字目が数字でない**ことも要る（7桁以上を黙って切り取らない）
```

保存形式は **`YYYY-NNNNNN`**（5桁の場合は `YYYY-NNNNN`）。`特願` は含めない。

> パディングしてから定数オフセットで切るのは、`substring` の範囲外エラーを
> **構造的に排除する**ため。検証スクリプト P3 が「検出処理の `substring` の第1引数は
> `outputs('Compose_*_Padded')` か `concat(...)` のみ」を機械確認する。

### 6.2 加減点

| 加点 | 減点 |
|---|---|
| 基礎 50 ／ **件名 +180** | **直前の引用 −20 ／ さらに古い引用 −60** |
| 現在の区画 +100 | 文脈に `別件/誤り/誤送信` **−80** |
| 文脈に `出願番号` +40 | |
| 文脈に `案件/標記/表題/本件` +20 | |
| 同じ番号が本文に複数回（2回+10／3回+20／4回+30／5回以上+40） | |

「同じ番号が複数回」は、設計書の `GROUP BY Number` の代替として
**その番号が本文に何回現れるか**で算出している（ループ不要で等価な値が得られる）。

**件名を強く優先する**のは補助資料の決定規則12による（件名 230 対 本文 150）。
採用根拠は診断の `applicationEvidence` に出る。

## 7. 信頼度と曖昧判定

内部にのみ保持する（SharePointの列にはしない）。

| 対象 | 判定 |
|---|---|
| 審査官名 | 空→`Not Found` ／ スコア<60→`Low` ／ 第2候補との差<15→`Ambiguous` ／ ≥180→`High` ／ それ以外→`Medium` |
| 出願番号 | 空→`Not Found` ／ 第2候補との差<15→`Ambiguous` ／ ≥160→`High` ／ ≥100→`Medium` ／ それ以外→`Low` |

`needsManualReview` は「どちらかが `Not Found` / `Low` / `Ambiguous`」または
「審査官名が確定していない（`FamilyNameOnly` / `HiraganaName`）」ときに true。

診断は `Compose_Detection_Diagnostics`（実行履歴で確認）に出力する。主なもの:

| キー | 内容 |
|---|---|
| `examinerNameType` | `FullName` / `FamilyNameOnly` / `HiraganaName` / `NotFound` |
| `primaryExaminerEmail` | 現在のメッセージに `特許庁の〈姓〉です` があり氏名が一致するときだけ送信元。他は空 |
| `primaryExaminerEmailEvidence` | `self-introduction-in-current` / `not-derivable` |
| `sourceSection` | `subject` / `current` / `quote1` / `quote2` |
| `examinerEvidence` / `applicationEvidence` | 適用されたスコア項目の内訳 |
| `completionSource` | `thread` / `none` |
| `examinerSpacingSource` | `original` / `variant` / `surname` / `none` |
| `ambiguityReason` | `not-found` / `hiragana-unresolved` / `multiple-family-name` / `score-tie` / `low-score` / 空 |
| `warnings` | 配列。`family-name-only` / `hiragana-name` / `examiner-low-score` / `application-ambiguous` / `application-not-found` |

ほかに 採用名・生の候補名・補完したか・採用パターン・スコア・第2候補との差・
スレッド深度・信頼度・候補数・一致文字列・要確認フラグ。

結果JSONには**集計のみ**を載せる:
`examinerFoundCount` / `applicationFoundCount` / `needsReviewCount` と、
**要確認のものだけ**を `detectionReviews[]`（100件でも肥大しない）。
`detectionReviews[]` には `examinerNameType` / `ambiguityReason` / `warnings` も含む。

> **メールアドレスは SharePoint の列にしない。** 名簿もメンバー一覧も使わず、
> 同姓者がいることを理由に人物を確定しない（補助資料§6）。
> アルゴリズムの詳細は [../../../docs/examiner_detection_spec.md](../../../docs/examiner_detection_spec.md)。

## 8. 既存リストが存在する場合

**7列すべてが必要**（利用者決定）。既存フローと同じ安全設計を維持する。

- 同名リストを再作成しない・削除しない・改名しない
- 既存列を削除しない・型を変更しない・ビューを変更しない
- 列が不足していれば `ERR_SCHEMA_INCOMPATIBLE` で**安全終了**し、
  `missingFields` / `incompatibleFields` に不足内容を返す。**メールも取得しない**

> 既存の5列リスト（`mail_tmp` 等）を指定すると
> `missingFields: ["ExaminerName","ApplicationNumber"]` で終了する。
> 新しいリスト名を指定すること。

## 9. 重複メールの扱い（既存と同一）

`MessageId`（`internetMessageId` 優先、無ければコネクタのID）をキーに
`$filter` で検索し、**0件→作成／1件→MERGE更新／2件以上→書き込まず記録**。
`$filter` の値は `''` 2重化＋`uriComponent()` の2段エスケープ。
`MessageId` 列には一意制約とインデックスを設定する。
作成が失敗した場合は再検索し、見つかれば更新へフォールバックする。

## 10. エラー時の動作

- 検出処理は **Compose / Query のみでコネクタを呼ばない**ため、実行時に失敗しない
  （検証スクリプト P4 が機械確認）。推定できなければ空文字を登録する
- 1件のメールの失敗は `itemErrors[]` に記録して次へ進む
- 全体エラー（入力不正・スキーマ不整合・権限）は `Scope_Handle_Error` が受け、
  `error.code` / `.stage` を結果JSONに出す

## 13. 既知の制約

| 制約 | 内容 |
|---|---|
| アクション数 | **491 / 500**。残り9。これ以上パターンやスロットを増やす余地はほぼ無い。増やす場合は子フローへの分割が必要 |
| 探索範囲 | 正規表現が無いため「全出現位置」は探せない。本文は先頭5件、審査官はパターンごと3件まで |
| スレッド深度 | **3段階まで**（現在／直前の引用／さらに古い引用）。3階層目と10階層目は区別できない |
| ひらがな氏名 | 漢字へ変換しない（読みの照合表が無い）。常に要確認になる |
| 審査官のメール | 自己紹介がある場合しか出せない。名簿・メンバー一覧からは引かない |
| `の` の除去 | 候補名の整形で `の` を除去する（`特許庁の山田`→`山田` のため）。`井の頭` のような `の` を含む姓は壊れる |
| 姓のみ補完 | 同一メール内に候補が1件だけのときのみ。名簿は使わない（プロジェクト内に存在しないため） |
| 姓名の空白（5文字以上） | 根拠が無い5文字以上の氏名は**切らない**（§5.7 規則E）。2＋3 と 3＋2 のどちらとも決められないため |
| 姓名の空白（4文字） | 根拠が無い4文字の氏名は 2＋2 で切る（規則D）。`林健太郎` のような**1文字姓＋3文字名**は `林健 太郎` と誤る。既知の3文字姓は表で救っているが、1文字姓は救えない |
| 3文字姓の表 | `KNOWN_SURNAMES_3` は20語のみ。表に無い3文字姓の4文字氏名（例 `神楽坂稔`）は 2＋2 で誤分割する。誤りを見つけたら表に追記する（`build_examiner_flow.py` の定数） |
| 部署宛名パターン | 行単位の走査ができないため「`様` の直前＋文脈の部署語」で近似している |
| 既存5列リスト | 使用できない（7列必須） |
| 編集時の重さ | 491アクションのため、デザイナーでの編集は重くなる（公式が500未満でも注意喚起している） |
