# doc-audit — 文書・Skill・実装の整合監査

## 不変則（全Skill共通・厳守）
definition.json は生成物。修正は必ず source/ の build_*.py を編集→再生成→検証。source/package/ の直接編集、references/・release/ 内の既存ZIPの上書き、原本（references/raw/・spec/の受領docx）の変更は禁止。Git操作は一切行わない。

## いつ使うか
文書が実装や運用と食い違っていないかを点検し、直すとき。定期的な棚卸しにも使う。
- フロー・案件・Skillを追加した後（索引の更新漏れが出やすい）。
- 「どの文書が正しいのか分からない」と感じたとき。
- 実行者への確認事項を整理・更新したいとき。

Power Automate の**定義そのものの正しさ**は対象外——それは flow-package-validate（`validate_*.py` / `tools/wdl_lint.py`）の担当。
本Skillが見るのは**文書体系の整合**（参照先の実在・数値の一致・役割の重複・古い記述）。

## 使う資材（すべて実在）
- `tools/doc_audit.py`（機械検査 C01〜C08）。
- `audit/README.md`（監査手順と正本の更新規則）。
- `audit/confirmations.json`（実行者への確認事項の**正本**）。
- `audit/findings/<日付>.md`（回次ごとの監査記録の**正本**）。
- `tools/gen_audit_docx.py`（正本 → 報告DOCX）。
- 正本となる索引: ルート `README.md`（案件一覧・フロー対応表）／ `CLAUDE.md`（構成マップ・不変則・Skill索引）。

## 手順

### 1. 機械検査（ベースライン取得）
`python tools/doc_audit.py` を実行し、**修正前の指摘件数を記録する**（後で「何件直したか」の根拠になる）。
`python tools/doc_audit.py --json` で機械可読の結果が得られる。

検査項目:
| ID | 内容 |
|---|---|
| C01 | 相対リンクの参照先が実在するか |
| C02 | インラインコードのパス表記が実在するか |
| C03 | Skill名・Agent名が frontmatter・ディレクトリ名・索引で一致するか |
| C04 | エラー件数等の数値が実際と一致するか |
| C05 | `error_catalog.md` が分割閾値（12エラー / 60KB）に達していないか |
| C06 | `build_*.py` / `validate_*.py` が実在するか |
| C07 | 各 `validate_*.py` が `tools/wdl_lint.py` を import しているか |
| C08 | 移動・改称済みの陳腐化パスが現行記述に残っていないか |

### 2. 機械検査で拾えない観点を人手で確認
スクリプトは「参照先の実在」までしか見ない。次は読んで判断する。
- **同じ仕様を複数の文書が違う説明をしていないか**（数値・手順・命名規則）。
- **古い前提が残っていないか**（案件が1つだった頃の記述・廃止した機能・旧バージョンの状態）。
- **役割の重複**（同じ内容が2箇所にあるなら、正本を決めて他方をリンクに置き換える）。
- **Skill / Agent の責務の重複・競合**、入力条件・出力形式・実行順序の食い違い。
- **実装との乖離**（文書が「実装済み」としているものが本当に在るか。テスト件数・フロー数）。

### 3. 現行仕様を確定させる
食い違いを見つけたら、**推測で決めずに根拠から確定する**。優先順位:
1. 実装（スクリプト・生成された definition.json・テスト結果ファイル）
2. 実行結果の記録（`validation/` の証跡・テスト結果 txt）
3. 複数文書の突き合わせ（新しい記述・具体的な記述を優先）

根拠が足りず確定できないものは**直さない**。(5) の確認事項へ回す。

### 4. 修正する（監査で終わらせない）
確定した現行仕様に合わせて、文書・Skill・Agent を実際に修正する。
- **正本を1つ決め、他はリンクにする**（同じ表を複数ファイルへ複製しない）。
- 古い記述は削除ではなく**経緯として1行残す**か、履歴側へ移す（過去の調査結果を失わせない）。
- 原因が Skill / Agent 側にあるならそちらを直す（文書だけ直しても再発する）。
- **機械化できる検査は `tools/doc_audit.py` / `tools/wdl_lint.py` へ足す**（文章のチェックリストで終わらせない）。

修正してはいけない範囲:
- `references/`（受領原本・展開）と `spec/` の受領docx——**編集禁止**。
- `_legacy/` 配下、各フローの過去 `validation/` レポート——**当時の事実の記録として凍結**する。

### 5. 確認事項を更新する（`audit/confirmations.json`）
実行者本人にしか確定できないものだけを登録する。書式と規則は `audit/README.md`。
- **新規は連番 `CONF-NNN` を採番**する。既存IDは再利用しない。
- **既に登録済みの内容を重複登録しない**（同一対象・同一趣旨なら既存項目を更新する）。
- 解消したものは**削除せず** `status` を `確認済み` / `対応不要` にし、`resolvedOn` を記録する。
- 「確認してください」で終わらせず、**実行手順・期待される結果・返してほしい情報**まで書く。

### 6. 記録と報告DOCXの生成
- 今回の発見・修正を `audit/findings/<YYYY-MM-DD>.md` に書く（**回次ごとに新しいファイル**。過去分を書き換えない）。
- `python tools/gen_audit_docx.py` で `audit/dist/` に日時付きDOCXを生成する。
- **DOCXを直接編集しない**。内容を変えるときは正本を直して再生成する。

### 7. 再検査
`python tools/doc_audit.py` を再実行し、**指摘0件**（または残件が確認事項として登録済み）であることを確認する。
併せて `python tools/wdl_lint.py --all .` が指摘0件のままであることを確認する（文書修正で REST 断片を壊していないか）。

## 出力（完了報告に必ず含める）
- 調査したファイル数と対象範囲。
- 指摘件数（修正前 → 修正後）と分類。
- 実際に修正したファイル一覧。
- 統合・役割変更した文書。
- 修正した Skill / Agent。
- 確認事項の件数（新規 / 更新 / 解消）。
- 生成したDOCXと正本の保存先。
- 未解決事項。

主要な不整合は **「修正前」「問題点」「修正後」** が分かる形で報告する（抽象的な要約で済ませない）。

## 停止条件（ユーザーへ確認する）
- 複数の仕様候補があり、**業務上どちらを採用するかで結果が変わる**とき。
- 文書やフローの**削除・統合・廃止**の最終判断が要るとき。
- 実環境でしか確認できない挙動に依存するとき。
- 修正が**実装の挙動を変える**とき（検証スクリプトの判定基準・生成ロジック等）。
  この場合は勝手に再生成・再パッケージせず、影響範囲を確認事項としてまとめる。

いずれも推測で確定させず、判断材料を添えて確認する。

## 連携（他Skill/Agentとの関係）
- **knowledge-update との境界**: あちらは「再利用できる知識」を `handbook/` へ書く。本Skillは「文書間の食い違い」を直し、記録を `audit/` に置く。同じ内容を二重に持たない。
- 定義・パッケージの正しさは flow-package-validate / package-auditor の担当。本Skillは踏み込まない。
- 監査中に見つけたフローの不具合は flow-error-fix / flow-update へ引き継ぐ（本Skillでは直さない）。
- 専用Agentは持たない（検査が決定的なスクリプトで完結するため。Agentを増やすと責務が重複する）。
