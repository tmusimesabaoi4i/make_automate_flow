# 教訓集（migrate_chat_spo 案件 / Teams課内会議アーカイブ）

Teams チャネルの課内会議アーカイブを SharePoint に移送する単一クラウドフローを作る過程で得た教訓を、
「結果」だけでなく「なぜその判断に変えたか」を含めて記録します。ルールの詳細は各ルールファイルへリンクします。

## 表記
- 【事実】= 案件で実証、または公式確認済み。 【推奨】= 事実から導いた指針。 【案件固有】= 今回だけの判断。
- 【要実環境確認】= 実環境で未検証。 公式資料の参照日は 2026-07-16。
- 実値は書かず `{teamId}` `{channelId}` `{siteUrl}` `{listId}` `{destinationPath}` を使う。

## 1. 最初の設計方針
- 【案件固有】Teams チャネルの会議投稿・返信・添付を収集し、整形して SharePoint に保存し、
  処理台帳と実行ログを残す、という一連の自動化を目標に置いた。
- 【案件固有】第1段階の成果物は設計資料のみで、当初は役割別の複数フロー（5フロー統合構成）として設計した。
- 【事実】最終成果物は手動トリガー（インスタントクラウドフロー）1本。取得→整形→保存→台帳→ログを1フローに集約した。

## 2. Azure 不使用方針への変更経緯
- 【案件固有】「Azure・プレミアム・独自コード・汎用HTTP・アプリ登録を使わない」は案件当初からの環境制約
  （一般ユーザー権限のみで完結させる要件）。管理者権限・アプリ登録を前提にできない環境だった。
- 【背景】Teams のメッセージは Microsoft Graph から取得する。素朴には Graph 呼び出しに
  Azure AD アプリ登録＋管理者同意（HTTP with Microsoft Entra ID / 旧 HTTP with Azure AD）が要ると考えがち。
- 【事実】しかし Teams 標準コネクタの「Send a Microsoft Graph HTTP request（operationId=HttpRequest）」は、
  標準接続だけで Graph GET を実行でき、Azure AD アプリ登録も管理者同意も不要と確認できた。
  この確認が「制約下でも要件を満たせる」判断の決め手になった。→ [04](../rules/04_connectors_permissions_and_dlp.md)。

## 3. 複数フロー → 単一フローへの変更理由
- 【背景】第1段階では役割別の5フロー統合構成で設計した（設計資料のみ）。
- 【変更理由1】第2段階の要件が「インポートできる実物のZIPを1つ・フロー1本」だったため。
  複数フロー＋子フローはZIPパッケージ・接続再マッピング・権限管理が複雑になる。
- 【変更理由2】運用が「定期実行」ではなく「システム移行前に過去2年分を一度に取得する一回性の処理」と
  判明したため、フロー間の状態受け渡し（配列・カウンター・実行状況）を作る利点が薄く、
  状態を1フロー内の変数で持てる単一フロー＋Scope整理が最も単純だった。
- 【推奨】分割は実行時間上限超過・共通処理の再利用・権限境界の相違などがあるときに限る。→ [01](../rules/01_flow_architecture_rules.md)。

## 4. サンプルZIP採用理由
- 【事実】レガシーパッケージ（.zip）の内部フォーマット詳細は公式に公開されていない。
- 【変更理由】そこで既存の配布済みパッケージ（雛形）と、実環境で動作実績のある実働サンプルの中身を解析し、
  5ファイル構造・接続参照の形式を雛形に合わせて生成した。ゼロから推測で組むより破損リスクが低い。→ [07](../rules/07_export_import_package_rules.md)。

## 5. SetVariable 自己参照エラー（最重要）
- 【事実】保存時に `WorkflowRunActionInputsInvalidProperty`（Self reference is not supported）が発生。
  「変数の設定（Set variable）」の値式に更新対象の変数自身（`union(自身, …)` 等）を含めていたのが原因。
- 【事実】検出は3件（`Set_MessagesArray` / `Set_RepliesArray` / `Append_Reply_Attachment_Candidates`）。
  3件目は名前が Append でも実体は SetVariable＋union。**名前でなく type を見る**。
- 【変更内容】配列は Append to array variable、文字列は Append to string variable、
  カウンターは Increment variable に置換した。→ [03](../rules/03_variables_arrays_and_objects.md)。

## 6. インポートできても保存できない問題
- 【事実】上記5はインポートでは検出されず、**インポート成功後の保存で初めて失敗**した。
- 【教訓】「インポートできた＝完成」ではない。インポート後は 開く→即保存→フローチェッカー→小規模テスト を必ず行う。→ [07](../rules/07_export_import_package_rules.md)。

## 7. サンプルフローから参考にできた点
- 【事実】Teams「Send a Microsoft Graph HTTP request」で Graph GET が標準接続で動く実装パターン。
- 【事実】チャネルID（`:` `@` を含む）の URL エンコード必須と、メッセージIDの `uriComponent()` 処理。
- 【事実】`body('<Graph HTTP>')` が Graph 応答JSONそのもの（封筒ではない）であること。
- 【事実】HtmlToText のパラメータキーが `Content`、SharePoint PostItem が dataset/table/item 形式であること。
- 【事実】接続参照キーに `-2` 等のサフィックスが付き、`host.connectionName` と一致させる必要があること。→ [05](../rules/05_sharepoint_and_teams_patterns.md)。

## 8. 流用できなかった点（サンプルにも設計バグはある）
- 【事実・アンチパターン】添付蓄積が SetVariable の上書きで、複数返信の添付が最後の1件しか残らない。
- 【事実・アンチパターン】ページング無し（`$top=50` の1ページのみ）で50件超が取得漏れ。→ [05](../rules/05_sharepoint_and_teams_patterns.md)。
- 【事実・アンチパターン】Parse JSON が封筒形スキーマで実参照パスと不一致（required 未評価で偶然通過）。
- 【事実・アンチパターン】取得前に既存項目を全削除（取得失敗時ロールバック不能）、値式末尾の `\n` 混入、
  タイムゾーン基準の不整合。→ 破壊的処理は取得成功後に。[05](../rules/05_sharepoint_and_teams_patterns.md)。

## 9. Teams コネクタの Graph 要求
- 【事実】Teams のメッセージ/返信取得は Graph 経由。URL は `{teamId}/{channelId}/messages` と
  `.../messages/{messageId}/replies`。チャネルIDは `uriComponent()` でエンコード、teamId は GUID で不要。
- 【事実】`$top=50` だけでは完了せず、`@odata.nextLink` を Do until で追跡して全件取得する。→ [05](../rules/05_sharepoint_and_teams_patterns.md)。

## 10. trim・coalesce・配列型の注意
- 【事実】基本形は `trim(coalesce(<文字列 or null>, ''))`。`coalesce(trim(x), '')` は禁止（null で trim 失敗）。
- 【事実】coalesce の候補は同一型（文字列 `''` / 配列 `json('[]')` / オブジェクト `json('{}')`）。
- 【事実】Apply to each の入力は配列保証（`coalesce(x, json('[]'))` か Filter/Select 出力）。
- 【事実】`@` はネスト関数に付けない（インポート式パースエラーの原因）。→ [02](../rules/02_expression_and_type_safety.md)。

## 11. Word 生成制約
- 【事実】標準コネクタだけで真正 .docx は動的生成できない（Word テンプレート機能はプレミアム）。
- 【案件固有】HTMLベースの Word 互換 `.doc` を採用。HTML を `.docx` にリネームするのは破損になるため禁止。
- 【事実】HTMLエスケープは `&` を最初に、改行は `<br>`、改ページは2件目以降のみ。→ [06](../rules/06_word_html_document_generation.md)。

## 12. 7日間から段階検証する方針
- 【変更理由】いきなり全期間（730日）を回すと実行時間上限（目安 約30分）や取得漏れのリスクが高い。
- 【推奨】`7日 → 30日 → 365日 → 730日` と対象期間を段階的に広げ、各段階で件数・失敗・成果物を確認する。
  上限を超えそうなら期間を分割して複数回実行する。→ [08](../rules/08_error_handling_and_idempotency.md)。

## 13. 今後、最初から行うべきこと
- 【推奨】変数更新は最初から専用アクション（Append to array/string、Increment）を使い、SetVariable 自己参照を作らない。
- 【事実→推奨】コネクタ（OpenApiConnection）出力のフィールドは `body('X')?['field']` で参照する。
  `outputs('X')` は封筒 `{statusCode, headers, body}` を返すため `outputs('X')?['field']` は**常に null**
  （正しくは `outputs('X')?['body/field']`）。本案件では設計監査で5箇所の潜在バグとして検出・修正した
  （DryRun既定では発火せず、本番経路でのみ全添付が保存失敗になるところだった）。
  ※Compose の `outputs('Compose_X')` は封筒を持たないためそのままでよい。
- 【推奨】インポート前に機械走査（JSON構文/runAfter整合/重複名/自己参照/重複初期化/接続突合/不正@/operationId実在/匿名化リーク）を回し、0件にする。
- 【推奨】実値はプレースホルダー化し、標準コネクタで完結する設計を優先する（Azure・管理者権限を前提にしない）。
- 【推奨】未確認事項は「要実環境確認」と明記し、公式で確認できないことは断定しない。

## 14. 今後、避けるべきこと
- 【禁止/回避】SetVariable での自己参照（配列 union / 文字列 concat / `add(自身,1)`）。
- 【禁止/回避】ネスト関数への `@` 付与、`coalesce(trim(...), '')`、coalesce 候補の型ずれ。
- 【禁止/回避】HTML の `.docx` リネーム、ページング省略、取得前の破壊的削除、Teams contentUrl の成果物流用。
- 【回避】「今回たまたま動いた」ことの無条件な一般化（例: 未エンコードURLでの動作を前提にしない）。
- 【回避】「インポート成功＝完成」という思い込み。保存・チェッカー・小規模テストまでを完了条件にする。

## 15. 保存時検証は1件ずつしか報告しない（もぐら叩き）＋ Create item の動的サイト/リスト制約
- 【事実】保存時のエラーダイアログは**1件ずつ**しか報告しない。今回は同型の`PostItem`
  （Create item）が4箇所あったが、1件直して保存し直すたびに次の1件が新たに報告される
  「もぐら叩き」状態になった。
- 【教訓】同種エラーが出たら1件の修正で満足せず、definition.json全体を機械検索して
  **同型パターンの残数**を確認してから再保存する。対症療法の繰り返しは手戻りの原因になる。
- 【事実】原因は`PostItem`の必須動的ボディ`item`が、`dataset`（サイト）/`table`（リスト）を
  **静的選択した場合のみ**列スキーマを解決できる制約による。式（変数）のサイト/リストでは
  `item`を構築できず`OpenApiOperationParameterValidationFailed`で保存が失敗する。
- 【推奨】サイト/リストを式にする必要があるなら`PostItem`ではなく
  「SharePoint に HTTP 要求を送信」＋RESTに置換する。→ [05](../rules/05_sharepoint_and_teams_patterns.md)、[エラーカタログ](./error_catalog.md)。

## 16. 静的検証で捕捉できない実行時エラー（クロスサイト参照）
- 【事実】今回の`GetFileContentByPath`の404は、**インポート成功→保存成功→実行時エラー**という
  3段階目で初めて顕在化した。「保存できた＝完成」でもないことが分かった。
- 【事実】原因確定の決め手は実行結果（実データ）の提供だった。Teamsチャネル添付の`contentUrl`が
  投稿のあるチームのサイト（`Shared Documents`配下）を指しており、保存先として別途指定していた
  サイト（`dataset`）と一致していなかった。机上の式検証だけでは気づけなかった。
- 【教訓】Teamsチャネルの添付ファイルは**投稿のあるチームのサイト**に保存され、保存先サイトと
  同一とは限らない。`contentUrl`を`/Shared Documents/`でサイトとパスに分割導出する。
  → [05](../rules/05_sharepoint_and_teams_patterns.md)、[エラーカタログ](./error_catalog.md)。
- 【教訓】ネスト深さが上限（8）ちょうどのフローで分岐を追加する場合、新規Scope追加ではなく
  既存Scopeの型を置き換える方式で深さを増やさずに対応する。→ [01](../rules/01_flow_architecture_rules.md)。

# 教訓集（teams_post_url_flows 案件 / Teams投稿URLから投稿・全返信を取得）

Teams投稿URLを入力として、対象投稿（Flow1）と全返信（Flow2）を取得する独立2フローを作る過程で得た教訓。
**2026-07-24に実環境でインポート・実行に成功**した案件のため、それまで「要実環境確認」だった事項のいくつかを
【事実】へ格上げできた。参照日・確認日は 2026-07-24。

## 17. 実環境で実証できたこと
- 【事実】Teams標準コネクタの `HttpRequest` で、**Graph の単一メッセージ取得**
  `GET /teams/{teamId}/channels/{channelId}/messages/{messageId}` が動作する。
  一覧・返信だけでなく、任意のメッセージIDで1件取得できる。→ [05](../rules/05_sharepoint_and_teams_patterns.md)。
- 【事実】`/replies` の取得も動作する（確認できたのは返信50件以下＝単一ページ）。
- 【事実】**匿名化した接続GUIDは、インポート時に選択した実接続へ正しく再マッピングされる。**
  従来は状況証拠のみだったが、インポート後に実行が成功したことで実証された。→ [07](../rules/07_export_import_package_rules.md)。
- 【要実環境確認】返信51件超の `@odata.nextLink` 追跡（複数ページ）は未確認のまま。
  **1ページに収まるスレッドでは、ページングが機能していなくても正常に見える**点に注意。

## 18. 「実行できた」と「結果が正しい」は分けて記録する
- 【教訓】本案件では「インポートできた・実行できた」という報告を受けたが、それは
  「全テストケースが通った」ことを意味しない。実際、最重要の未確認項目（返信51件超のページング）は
  そのまま残った。
- 【背景】migrate_chat_spo では**フローがエラーなく完走したのに添付が全件失敗**していた事例がある
  （[エラーカタログ](./error_catalog.md)）。完走は結果の正しさを保証しない。
- 【推奨】実環境確認を受けたら、**何がどこまで確認されたのかを具体的に確かめてから**
  ドキュメントの「要実環境確認」を外す。まとめて「動作確認済み」にしない。

## 19. `if()` は両分岐を先行評価する
- 【事実】`if(条件, 真, 偽)` は条件の真偽に関わらず**両方の引数を評価する**。
  「条件で守っているから安全」は成り立たない。
- 【事実・アンチパターン】`if(endsWith(P,'/'), substring(P, 0, sub(length(P),1)), P)` は
  `P` が空文字のとき長さ `-1` となり、条件が false でも実行時エラーになり得る。
- 【推奨】長さ計算を伴う `substring` を分岐に置かず、`split`→`take`→`join` で代替する。
  空文字でも安全に空文字を返す。→ [02](../rules/02_expression_and_type_safety.md)。

## 20. 使用関数を「実績のある集合」に機械的に閉じ込める
- 【背景】指示書で例示された関数（`uriQuery()` `uriPath()` `uriComponentToString()`）に、
  本リポジトリ内の使用実績が無いものが含まれていた。公式に存在しても、挙動の細部
  （`uriPath()` がパス中の `%3A` を復号するか等）が確認できないものは採用リスクがある。
- 【推奨】**検証スクリプトに「関数許可リスト検査」を実装する**。定義中の全 `関数名(` を抽出し、
  実働実績のある集合に含まれることを機械確認する。推測での関数採用を構造的に防げる。
- 【事実】クエリ解析は `split()`、URLデコードは `decodeUriComponent()` で代替できた。
  実績のある関数だけで要件を満たせるなら、そちらを選ぶ。→ [02](../rules/02_expression_and_type_safety.md)。

## 21. Catch用 Scope の runAfter は「最後の1本」にだけ張る
- 【事実】`runAfter` に複数のアクションを列挙すると **AND判定**になる。
  Try相当の全Scopeを `[Failed, Skipped, TimedOut]` で列挙すると、
  「前段は成功・中段が失敗」というよくあるケースで前段が `Succeeded` のため条件を満たさず、
  **ハンドラが発火しない**。
- 【推奨】Scopeを直列に連鎖させ、Catch用Scopeの `runAfter` は**直前の最終Scope1本だけ**に張る。
  途中で失敗すれば後続Scopeは `Skipped` になるため、最終Scopeの `Skipped/Failed/TimedOut` で
  どの段階の失敗も確実に捕捉できる。→ [01](../rules/01_flow_architecture_rules.md)。

## 22. 想定内エラーと想定外エラーで結果生成の経路を分ける
- 【推奨】入力検証で弾ける「想定内エラー」は、Scopeを失敗させずに**正常系の中で分岐**して
  エラー形式の結果を組み立てる。コネクタ失敗などの「想定外エラー」だけを Catch Scope で受ける。
- 【理由】この分離により、成功側の式だけが `body('<コネクタ>')` を参照する形にできる。
  失敗側・ハンドラ側は変数だけを参照するため、**コネクタがスキップされていても式が壊れない**。
  → [08](../rules/08_error_handling_and_idempotency.md)。
- 【推奨】ハンドラで診断情報（HTTPステータス・処理段階・途中までの取得件数）を使いたい場合は、
  `runAfter=[Succeeded, Failed]` のSetVariableで**変数へ退避**しておく。
  → [../knowledge/expression_examples.md](./expression_examples.md) 15-D。

## 23. 生成物そのものを検証する（設計書の再実装を検証しない）
- 【推奨】式ロジックの検証は、設計書を読んで別実装したものではなく
  **生成済み `definition.json` の式文字列そのもの**を評価して行う。
- 【案件固有】本案件ではWDL式のミニ評価器（対象フローが使う関数のサブセットのみ実装）を作り、
  `definition.json` から解析用Scopeを読み出して入力URLごとの結果を期待値と突き合わせた。
  実機を使わずに正常系・異常系20ケースを回帰テストできる。
- 【注意】この方式で確認できるのは式の論理であって、実機での関数の挙動差・コネクタ応答ではない。
  何が確認でき何が確認できないかを、検証レポートに明記する。

## 24-A. 「動的サイト」は HttpRequest なら組める（実証）
- 【事実】任意の SharePoint サイトを実行時に決めるフローは、`HttpRequest` の `dataset` に式を渡せば組める。
  2026-07-24 に create_initialized_sharepoint_list を実環境でインポート・実行して確認した
  （16アクション全てが `@variables('varSiteUrl')`）。
- 【経緯】着手時点では本リポジトリの SharePoint フロー2本がいずれも `dataset` を静的リテラルにしており、
  「式で保存できるか」が案件最大のリスクだった。`error_catalog` にも「演繹であり実働実績はない」と書かれていた。
  **リスクとして明記したまま実装し、実環境で確認して事実へ格上げする**という進め方が機能した。
- 【推奨】未確認の前提に依存する設計をするときは、(1) その1点を最上位リスクとして文書の目立つ場所に書き、
  (2) 失敗した場合の切り分け手順と代替案を先に用意しておく。実機確認後に文書を更新する。
  → [../knowledge/sharepoint_rest_list_provisioning.md](./sharepoint_rest_list_provisioning.md) §11

## 24-B. 破壊的操作の対象は「名前」でなく「ID」で指定する
- 【推奨】列削除・ビュー変更・リスト削除など**取り返しのつかない操作のURIには、必ずリソースID**を使う。
  リスト名で対象を特定すると、名前の取り違えや同名リストの存在で**既存の業務データを壊しうる**。
- 【推奨】これは設計方針ではなく**機械検査で担保する**。次の2点を検証スクリプトに入れると構造的に防げる。
  - 定義中に `GetByTitle(` が **0件**であること
  - 書き込み系REST（POST/MERGE/DELETE）のURIに、今回作成したリソースのID変数が**必ず含まれる**こと
- 【事実】create_initialized_sharepoint_list ではこの2検査に加え、
  「初期化系アクションが `varCreatedInThisRun == true` のガード配下にあること」
  「同名確認が作成より runAfter 順で前にあること」
  「作成失敗経路にREST呼び出しが無いこと」も走査し、既存リスト保護を静的に保証した。
- 【教訓】**安全性は「気をつける」ではなく「その経路を定義から消す」ことで担保する。**

## 24-C. 「実行成功」は経路ごとに分けて記録する
- 【事実】create_initialized_sharepoint_list は実環境で `status: Created` を返したが、
  これは**新規作成経路だけ**が通ったことを意味する。
  同名リストが存在する場合の経路（＝このフローの最重要の安全機構）は一度も発火していない。
- 【推奨】分岐の多いフローでは「実行に成功した」で終わらせず、**どの経路が通ったか**を記録する。
  失敗経路（ロールバック・権限不足・競合）は正常系の確認では絶対に通らない。
- 【推奨】結果JSONに `status` を持たせておくと、この切り分けが実行履歴だけで済む。

## 24. 共通ツールのハードコードに注意
- 【事実】`tools/gen_outline.py` がトリガー入力名を前案件の値でハードコードしており、
  別フローのアウトラインに誤った入力名が出力されていた。定義から読む形に修正した。
- 【推奨】案件をまたいで使うスクリプトは、**案件固有の値を埋め込まない**。
  流用時は出力を1度目視し、前案件の残骸が混ざっていないか確認する。

## 26. 「式は全部正しい」と「インポートが通る」は別【実発生】

- 【事実】トリガー入力の**説明文**に書いた `例: shared-mailbox@{tenant}.example.com` が原因で

- 【事実】`{tenant}` のような**波かっこ単体は安全**（同じ文字列を含むパッケージが
  実環境インポートに成功している）。危険なのは **`@` と `{` が隣接する場合だけ**。
- 【教訓】メールアドレスの例をプレースホルダー付きで書くと、直前が必ず `@` になり `@{` が生まれる。

## 27. 検査の穴は「自分が想定した範囲しか見ていない」ことで生まれる【最重要】

  修正前のパッケージに新しい検査を当てて「検出できること」を確認してから修正版を作る

## 29. 403 は「権限」と決めつけない【実発生】

## 30. 文脈窓は「前後」ではなく、意味の向きに合わせて取る【実発生】
- 【事実】候補語の周辺を見て加減点するとき、窓を無条件に「前後64文字」にすると
  **後ろにある無関係な記述が前の候補を巻き込む**。
  実例（sync-mail-to-list-with-examiner-detection / 2026-08-04）:
  「宛名の審査官へ挨拶 → その直後に差出人（弁理士）の署名」というごく普通のメールで、
  宛名の審査官が「外部関係者」と判定されて −100 され、検出できなかった。
- 【推奨】窓を決める前に「その手掛かりは対象の**前**に来るのか**後ろ**に来るのか」を言語化する。
  - 修飾語・肩書き・所属（`弁理士`『特許事務所』など）は対象の**前**に来る → **直前だけ**を見る。
  - 除外の手掛かり（`Cc:` `陪席` `参加者`）も**前**に来る → 直前だけを見る。
  - 前後を見てよいのは、本当に位置が定まらない手掛かりだけ。
- 【推奨】窓の広さは「広いほど拾える」ではない。**広い窓は誤判定も広く拾う**。
  同じ理由で発生した不具合が本案件だけで3件（陪席の巻き込み・外部関係者の巻き込み・Cc の巻き込み）。
- 関連: `knowledge/lessons_learned.md` §27（検査の穴は想定範囲の外で生まれる）。

## 31. 「消し漏らし」は列挙で潰さず、構造で決める【最重要・実発生】
- 【事実】不要語を除去リストで消す方式は、**リストに載っていない実値**を消せない。
  実例（審査官名の抽出 / 2026-08-04）: 宛名行が
  `＊＊＊＊＊＊＊＊ 審査◯◯部◯◯◯ 山田太郎 審査官殿` の形で届き、
  既知の組織名しか消せないため `＊＊＊＊＊＊ 審査◯◯部◯◯◯ 山田太郎` が残った。
  結果は誤った値になるだけでなく、**長すぎて妥当性検査に落ち「空」になる**ケースもあった。
- 【推奨】列挙（ブラックリスト）を足し続けるのではなく、**位置・区切り・長さの構造**で決める。
  上の例では「人名は空白区切りの**末尾1〜2トークン**、それより前は組織名」という規則にした。
  直前トークンに長さ2〜3を要求すると、姓は通り部署名は通らない。
- 【推奨】列挙が有効なのは**閉じた集合**だけ（HTMLエンティティ、全角数字など）。
  相手が自由に決める値（部署名・社名・宛名の装飾）に列挙で立ち向かわない。
- 【推奨】誤検出の報告を受けたら「その語を除去リストに足す」で終わらせない。
  **同じ形の入力が他にいくつあるか**を考え、構造規則に置き換えられないかを先に検討する。
- 関連: §27（検査の穴は想定範囲の外で生まれる）、§30（文脈窓は意味の向きに合わせる）。

## 32. 抽出の失敗は「誤った値」だけでなく「空」としても現れる【実発生】
- 【事実】切り出しに余計な文字列が残ると、後段の妥当性検査（長さ上限・数字を含まない等）に
  引っかかって候補ごと落ち、結果が**空**になる。
  「空だった」を「そもそも該当が無かった」と読むと、原因を取り違える。
- 【推奨】検出系の診断出力には、**採用値だけでなく候補数と落ちた理由**を残す
  （本案件では `examinerCandidateCount` と採用パターン・スコアを診断に出している）。
- 【推奨】テストケースには「誤った値になる」ものと「空になる」ものを**両方**入れる。
  前者だけだと、同じ根本原因の後者側を取りこぼす。

## 33. 推測で補完するくらいなら、補完しないほうがよい【設計判断】
- 【事実】「日本の姓は2文字が大半」といった統計的な決め打ちで文字列を分割すると、
  例外（佐々木・長谷川などの3文字姓）を**必ず**誤る。
  誤って分割した値は、分割しなかった値より**質が悪い**——後者はただ不完全なだけだが、
  前者は「正しそうに見える誤り」として下流に流れる。
- 【推奨】補完・分割・正規化の根拠は、**同じ入力の中に実在する事実**から採る。
  実装例（審査官名の姓名分割 / 2026-08-04）:
  1. 既に区切られていればそれを使う
  2. 同じ入力内に「区切られた同一表記」があればそれを使う
  3. 同じ入力内に「その値の接頭辞になっている短い表記」がちょうど1つあればそこで切る
  4. どれも無ければ、**曖昧さが無い範囲でだけ**既定に落とす
  候補が2つ以上ある（曖昧な）ときは、その根拠は使わない。
- 【事実】ただし「根拠が無ければ常に何もしない」は行き過ぎになることがある。
  実データでは、空白付き表記も姓のみ表記も**どこにも現れない**氏名が多数あった。
  本案件では最終的に「4文字ちょうどの氏名は2＋2で切る／5文字以上は切らない」を既定にした。
  **曖昧さが小さい範囲に限って既定を持つ**のが落としどころ。
- 【推奨】採用根拠を診断出力に残す（例: `spacingSource = original / variant / surname / none`）。
  実行履歴を見れば「なぜそう補完したか」を後から検証できる。
- 【推奨】この方針は「未検出」を増やす。**それは仕様として明記する**
  （本案件では「1文字姓は分割しない」を既知の制約として文書化した）。
  静かに間違えるより、できないことを宣言するほうがよい。

## 34. 除外は「その人物」ではなく「その出現位置」に対して行う【設計判断】
- 【事実】「Cc に載っている人は候補から外す」を**氏名単位**で実装すると、
  本文で明示的に役割を与えられている同一人物まで巻き添えで消える。
  逆に「Cc だから減点する」だけだと、候補がそれしか無いときに採用されてしまう。
- 【推奨】除外は**出現位置ごと**に判定する。同じ氏名が別の箇所でより強い根拠とともに
  現れていれば、そちらの候補が生き残って採用される。
  結果として「その属性だけを理由に人物を否定しない」と「弱い根拠だけでは採用しない」を同時に満たせる。
    - Cc欄に同姓の別人がいて本文に明示の担当者がいる → 本文側が採用される
    - Cc欄にしか記載が無い → 採用しない（証拠が1つだけ）
- 【推奨】名簿・メンバー一覧に同姓者がいることを理由に人物を確定しない。
  一覧は「候補の存在」を示すだけで、「この人物である」ことの根拠にはならない。
- 関連: [[30]] 文脈窓は意味の向きに合わせる、[[33]] 推測で補完するくらいなら補完しない。

## 35. 桁数を揃えた文字列をソートキーにするなら、範囲を生成時に検査する【実発生】
- 【事実】`sort` が昇順の**文字列**比較しか持たない環境で、数値スコアを
  `string(score + 10000)` のようにしてキーにするのは定番だが、
  **スコアが負になった瞬間に桁数が落ちて大小が逆転する**（`"9990" > "10150"`）。
  実例（2026-08-04）: 減点項目を1つ増やしたら、無関係に見える既存テストが1件落ちた。
- 【推奨】「オフセット＋スコアが常に同じ桁数」であることを**生成時に assert する**。
  定数表から最小値・最大値を計算して範囲を確かめれば、点数を足すたびに人が考えなくて済む。
```python
def _assert_sort_key_width(table, bases, label):
    neg = sum(v for v in table.values() if v < 0)
    pos = sum(v for v in table.values() if v > 0)
    lo, hi = OFFSET + min(bases) + neg, OFFSET + max(bases) + pos
    assert 10000 <= lo and hi <= 99999, label
```
- 【推奨】同点時の順序も**キーに埋め込んで決定的にする**。実行環境の `sort` の
  安定性は保証されていないため、同点を放置すると結果が不定になる。
- 関連: `knowledge/expression_examples.md` §14（sortは昇順のみ・降順はreverse併用）。

## 36. オフライン評価器が実機より緩いと、テストは「動くこと」を証明しない【最重要・実発生】

- 【事実・実発生】2026-08-04、teams-channel-member-sync が実環境で
  `substring parameter is out of range` により実行時失敗した。
  原因は「`substring` の開始位置は文字列長より**小さい**必要がある」という仕様で、
  空文字には `substring('', 0, 0)` すら適用できない。
- 【問題の本質】この案件には**空文字入力のテストケースが最初から存在していた**（管理サイトURL未設定・
  サイトURL空）。にもかかわらず合格していたのは、`tools/wdl_eval.py` の `substring` が
  `start == length(s)` を許容していて**実機より緩かった**ため。
  → **テストが緑であることは「自分の評価器で通った」以上を意味しない。**
     評価器の厳密さが、テストの証明力の上限を決める。
- 【事実】評価器を実機の文言どおり（`start < length`）に厳密化したところ、
  **別案件（sync-shared-mailbox-to-sharepoint-list）の同型バグ3件が即座に検出された**。
  1つの仕様差の修正が、リポジトリ全体の同型パターンを一度に洗い出した。
- 【推奨】実機のエラー文言を手に入れたら、まず**評価器のセマンティクスを直す**。
  フロー側だけ直すと、同じ誤りが次の案件で再び書かれる。
  評価器はリポジトリ全体で共有されているので、そこを直せば全案件のテストが自動的に強くなる。
- 【推奨】「静的検査で閉じられるか」を必ず併せて考える。今回は
  「`substring(` は必ず `substring(concat(` の形で書く」という規約にしたので、
  文字列一致だけで機械検査できる（`flow_checks.py` の P16）。
  一般の空文字判定は静的には決定不能だが、**書き方を1つに固定すれば検査可能になる**。
- 【注意】この検査を `tools/wdl_lint.py` へ入れることは見送った。既存4案件の `substring` には
  If アクションや構成上の保証で安全なものが多く、一律にエラーにすると偽陽性で
  他案件の検証が止まるため。**規約は案件内で閉じ、知識は handbook に置く**という分担にした。

## 37. インポート後の手作業を前提にすると、「未設定」が既定になる【実発生・設計判断】

- 【事実・実発生】2026-08-04、teams-channel-member-sync の初期設定フローが2回続けて
  `ERR_ADMIN_SITE_NOT_SET`（インポート後に設定するはずの値が空）で止まった。
  フロー自体は設計どおり動いており、バグではない。**設計そのものが悪かった。**
- 【教訓】**インポート後の手作業を前提にした設計は、その手作業が抜けた状態が既定になる。**
  「READMEに書いてある」「エラーメッセージが親切」は解決策ではない。
  利用者が最初に触るのは手順書ではなく実行ボタンである。
- 【推奨】設定項目ごとに「実行時に分かるか」を必ず問う。分かるなら設定にしない。
  今回は、手動フローは**入力から分かる**（同期先サイトへ倒せる）ため設定を不要にできた。
  Recurrence トリガーのフローだけは入力が無く、レガシーパッケージには環境変数も無いため
  実行時に知る手段が本当に存在せず、そこだけ設定が残った。
  → **「両方に必要」と「片方だけ必要」を区別せずに一律必須にしていたのが誤り。**
- 【推奨】どうしても設定が残る箇所は、**値を提示する側のフローに提示させる**。
  本案件では手動フローの結果に `adminSiteUrl` と `nextAction`（貼り付ける値そのもの）を出し、
  利用者が値を探さなくて済むようにした。
- 【推奨】この種の後退は静的検査で固定できる。本案件では
  「未設定時の退避経路が存在する」「手動フロー側は未設定を失敗として扱わない」
  「結果に次の操作の案内がある」を検査にし（S05 / S06）、
  わざと壊して発火することを回帰テストで確認している（R24〜R26）。
- 【関連】要件に「インポート先環境での再設定方法」がある場合、
  **再設定の手数そのものを設計対象として数える**。手数は仕様ではなく設計の結果である。

## 36. 「N個ぶん展開した処理」はループへ畳むとアクション上限が一気に空く【実発生】
- 【事実】列・項目ごとにアクションを展開して書くと、**項目1つあたりの単価**が積み上がる。
  実例（2026-08-04 / sync-mail-to-list-with-examiner-directory）:
  SharePoint リストの列処理が**1列あたり12アクション**（作成6＋スキーマ検証5＋ビュー1）で、
  7列で122アクション。5列足すと上限500を超えて実装不能になった。
- 【推奨】項目定義を**1つの Compose に配列として置き**、`Apply to each` で回す。
  REST の呼び方も順序も変えずに、**項目数によらず一定**にできる。
  上の例では 122 → 51 になり、**以後は列を増やしてもアクションが増えない**。
```
Compose_Field_Definitions   [{internal, display, type, xml}, ...]   ← 1アクション
Foreach_Create_Field        並列オフ・内側4アクション
Foreach_Add_View_Field      並列オフ・内側1アクション
Foreach_Verify_Field        並列オフ・内側2アクション
```
- 【推奨】**並列オフ（`concurrency.repetitions = 1`）は必須**。変数を更新するだけでなく、
  ビューの列順のように**順序が結果に出る**処理では並列化すると再現性が失われる。
- 【推奨】ループの本体は `items('<ループ名>')?['key']` を参照する。
  URI ビルダーが項目名をリテラルとして埋め込む作りだと `@{...}` の入れ子になって式が壊れるので、
  **連結の項として式を受け取る版**を別に用意する（`field_uri_expr()`）。
- 【推奨】ループ化すると「列ごとのアクションが存在すること」を見ていた検査が全滅する。
  検査は**「定義配列の内容と順序」＋「ループがその配列を回していること」**へ置き換える。
  チェックの粒度を落とさないこと（ループの中身が空でも通る検査にしない）。
- 【事実】ガード配下でしか動かないスコープでは、**冗長な存在確認を外せる**。
  上の例では列作成が「この実行で作ったばかりの空リスト」でしか動かないため、
  列の存在確認（1列2アクション）は構造上不要だった。
- 関連: [[35]] 桁数を揃えたソートキー、[[31]] 列挙で潰さず構造で決める。
